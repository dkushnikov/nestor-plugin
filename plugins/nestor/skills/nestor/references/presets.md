# Council Presets — Model Rosters and Fallbacks

Defines the five model rosters Nestor uses when routing a consultation. The `arch` / `code` / `research` / `brainstorm` / `quick` presets map to distinct frontier-model combinations optimised for different question shapes. Nestor's router selects the preset; this file defines what each preset actually contains.

## Composition principle

Three rules govern roster membership, in priority order:

1. **No synthesizer-family models.** The chair/synthesizer is the calling session — in Atlas a Claude (Fable 5.1 / Opus-class). The synthesizer's lab is excluded from every roster: the chair already contributes that perspective during synthesis, and a same-lab member maximises correlated error exactly where the council must be independent — pressure-testing hypotheses the session itself built. This extends the 2026-05-10 design-review decision (which removed Anthropic from `brainstorm`/`quick`) to all presets. *A different chair (e.g., an OpenAI-model host) would need a different exclusion, decided in design review — never by swapping seats at runtime.*
2. **Compose by co-failure, not by headcount.** Ensemble gain tracks *low pairwise error overlap*, not member count or nominal diversity (arXiv 2607.20768: majority voting beat the strongest member in only ~10% of 3-model subsets; the only robust predictor of gain was low error overlap. arXiv 2606.27288: ensembles are capped by the simultaneous-failure rate, which naive estimates undercount ~2.5×). Prefer a slightly-weaker member from a distinct training lineage over a stronger one that fails together with the chair.
3. **Reliable delivery is a membership requirement.** All council traffic flows through OpenRouter; a member is only as good as the endpoint that answers. Prefer models served first-party (single vendor-owned endpoint pool). Open-weight models served by a broad third-party pool carry structural delivery risk: every call is a provider lottery — `moonshotai/kimi-k3` (15 endpoints, ~13 providers, one at 77% uptime with a 16k output cap) failed its `arch`/`code` seat on latency and empty responses despite frontier quality (see 2026-08-22 refresh). Before seating a member, check `openrouter.ai/api/v1/models/<id>/endpoints`. pal cannot pin a provider (no `provider` passthrough), so a pool that turns mixed after seating is a re-check trigger, not something the call can route around.

**Rollback condition** (falsifiable, per kill-criteria discipline): review after ~10 `arch`/`code` runs on the current roster using the run-metadata records (`models_used` / `degraded` / `stage2` / `background` fields make this computable). Triggers: (a) the council repeatedly misses failure modes that session-side review then catches — restore `anthropic/claude-opus-5.5` to whichever preset(s) the misses occurred in (`arch`, `code`, or both); (b) degraded-run rate on a newly seated member exceeds ~2 of 10 runs — first fix the failing slot via its fallback chain, and only then reconsider composition; (c) *(added v0.7.0)* a seat is background-delivered (> 120 s foreground window) in more than half of its calls over 10 runs — that is a wall-clock cost the review must weigh even when nothing fails. Either action is a design-review decision, logged in the refresh history. Condition (b) has fired once: kimi-k3, 2026-08-22. Condition (c) is what moved Qwen out of `arch`/`code` on 2026-10-27 (19 of 22 stage-2 calls backgrounded).

## Fallback chains per vendor

If a model returns an error or an unusable answer, the replacement comes from the **same vendor** to preserve cross-provider diversity. A seat cannot be swapped inside a running `pal.consensus` workflow (pal reads `models` only at step 1 — see `consensus-execution.md`); the seat is restored after the workflow with one `pal.chat` to the first fallback below, same packet and stance, one attempt (Nestor SKILL.md Step 4; decision 2026-10-28).

Chains are written with **full OpenRouter IDs** — the same rule as the preset table; a bare model name passed to pal falls through to its frozen alias registry and 404s or resolves stale.

- **OpenAI** (reasoning slots, `arch` / `research`): `openai/gpt-6-astra` → `openai/gpt-6.1-sol` → `openai/gpt-6.1-terra`
- **OpenAI** (code slot, `code` preset only): `openai/gpt-6-astra` → `openai/gpt-6.1-sol` → `openai/gpt-5.3-codex` — codex kept as deliberate code-specialist fallback
- **OpenAI** (quick slot): `openai/gpt-6-luna` → `openai/gpt-5.6-luna`
- **Google**: `google/gemini-4-argon` → `google/gemini-3.8-flash` → `google/gemini-3.1-pro-preview`; in `quick`, `google/gemini-3.5-flash-lite` → `google/gemini-3.1-flash-lite`
- **Moonshot** (`arch` / `code`): `moonshotai/kimi-k3.1-pro` → `moonshotai/kimi-k3` — the fallback shares the August delivery risk (third-party pool); if K3.1 Pro's own pool turns mixed after the open-weights release (promised 2026-11-04), that is a re-check, not a silent acceptance
- **DeepSeek**: `deepseek/deepseek-v4-pro-0813` → `deepseek/deepseek-v4-pro` (0423 weights) → `deepseek/deepseek-v4.1-flash`; in `quick`, `deepseek/deepseek-v4.1-flash` → `deepseek/deepseek-v4-flash`

- **xAI**: `x-ai/grok-4.7` → `x-ai/grok-4.6` → `x-ai/grok-4.5` — three live generations
- **Perplexity** (`research` preset only): `perplexity/sonar-pro-search` → `perplexity/sonar-deep-research` (fallback only: a lead generator with a 2024 skew, > 3 min per call)

Report the substitution to the user — do not silently swap vendors. Vendor diversity is what the preset provides; a silent cross-vendor swap breaks that.

Removed vendors: **Anthropic** (no roster slots remain — the chair supplies the perspective; see Composition principle; `claude-opus-5.5` is the rollback-(a) candidate), **Meta** (`muse-spark-open`, 2026-10-15, is open but served only by a six-provider third-party pool — rule 3; re-check if a first-party endpoint appears). Qwen left `arch`/`code` on 2026-10-27 (latency, not quality) and stays in `brainstorm`.

### Vendor singletons

None in the current rosters — every vendor slot has an in-vendor fallback chain (Perplexity's and Moonshot's are two-deep). If an entire vendor chain is exhausted during a run, that is the **degraded-run case**: do not cross-vendor swap; proceed with the remaining models and flag the roster degradation in the return envelope's `confidence` field per Nestor SKILL.md Step 4.

## Presets are authoritative at runtime

The preset rosters are **spec-level decisions**. At runtime, the calling session acting as Nestor must use the exact models listed above for the chosen preset. Do not deviate based on reasoning about correlation, synthesizer overlap, redundancy, or any other optimisation target — even if the reasoning is internally consistent.

If you have an argument for changing a preset roster — for example, *"the synthesizer is Claude, so including Claude models in the roster correlates errors and should be swapped out"* — surface it to the user as a spec discussion. Do not act on it unilaterally. Runtime deviations break reproducibility across runs and make kill-criteria metrics noisy, and the judgment "this optimisation is safe" cannot be validated at runtime — only in design review.

If the full preset cannot respond because of infrastructure failure (model unavailable, timeout, parse error), that is the **degraded-run case** — flag the missing model in the return envelope's `confidence` field per the degraded-run handling described in Nestor SKILL.md Step 4. Do not pre-emptively deviate for optimisation reasons and label the result as a degraded run after the fact.
